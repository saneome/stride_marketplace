## 1. Общее описание проекта

Веб-приложение представляет собой площадку для размещения и поиска объявлений
о продаже бывших в употреблении товаров. Система включает **публичную часть**
(доступна всем пользователям из интернета) и **административную панель**
(доступна только из внутренней сети / через VPN).

## 3. Архитектура

Интернет
│
▼
┌─────────┐
│  Nginx  │ :80 / :443
└────┬────┘
│
├──── /api/*          ──▶ backend (FastAPI)      :8000
├──── /               ──▶ frontend-public        :3000
├──── /uploads/*      ──▶ minio / static volume
│
│  (deny all для /admin/* снаружи)
│
└──── внутренняя Docker-сеть ──────────────────────┐
│
WireGuard :51820/udp ──▶ внутренняя сеть ──┐            │
▼            ▼
admin-frontend ──▶ backend /admin/api/*
:5173           :8000
PostgreSQL :5432 (только внутренняя сеть)
Redis      :6379 (только внутренняя сеть)
MinIO      :9000 (только внутренняя сеть, консоль :9001)

Все сервисы объединены во **внутреннюю Docker-сеть**. Наружу проброшены только
порты Nginx (80, 443) и WireGuard (51820/udp). Ни один другой сервис не имеет
прямого выхода в интернет.

**Docker-сети:** `external` (nginx, wireguard → интернет) и `internal`
(все сервисы). Nginx и WireGuard являются мостами между сетями.

## 5. API — публичная часть

Все эндпоинты под префиксом `/api/v1/`.

### 5.1. Аутентификация (`/api/v1/auth`)

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/register` | Регистрация (email + пароль). Возвращает `201`. |
| POST | `/login` | Вход. Возвращает пару `access` / `refresh` JWT. Если у пользователя включена 2FA — возвращает `202` с промежуточным `totp_token` и требует прохождения `/login/totp`. |
| POST | `/login/totp` | Подтверждение TOTP-кода после пароля. Принимает `totp_token` + `code`. Возвращает JWT-пару. |
| POST | `/refresh` | Обновление access-токена по refresh-токену. |
| POST | `/logout` | Инвалидация refresh-токена (Redis blacklist). |
| POST | `/request-password-reset` | Отправка ссылки на сброс пароля на email. |
| POST | `/reset-password` | Установка нового пароля по одноразовому токену. |

### 5.2. Двухфакторная аутентификация (`/api/v1/auth/totp`)

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/enable` | Генерирует `totp_secret`, возвращает QR-код (base64) и секрет. Требует подтверждения через `/confirm`. |
| POST | `/confirm` | Принимает TOTP-код, активирует 2FA (`totp_enabled = true`). Возвращает набор одноразовых recovery-кодов. |
| POST | `/disable` | Отключение 2FA (требует текущий TOTP-код + пароль). Для `admin` запрещено. |

### 5.3. Профиль (`/api/v1/users`)

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/me` | Текущий пользователь. |

| GET | `/{id}/listings` | Публичные активные объявления пользователя. |
| GET | `/{id}` | Публичный профиль (display_name, avatar, дата регистрации). |

### 5.4. Объявления (`/api/v1/listings`)

| GET | `/` | Список. Пагинация (cursor-based или offset). Фильтры: `category_id`, `price_min`, `price_max`, `condition`, `location`, `q` (полнотекстовый поиск). Сортировка: `created_at`, `price`, `views_count`. |
| GET | `/{id}` | Детальная страница. Инкремент `views_count` (debounce через Redis — не чаще 1 раза в 10 мин с одного IP/user). |
| POST | `/` | Создание (авторизация обязательна). Статус → `moderation`. |
| PATCH | `/{id}` | Редактирование (только автор, только статусы `draft` / `rejected`). При редактировании статус возвращается в `moderation`. |

| GET | `/listings/{id}` | Детали объявления (включая историю статусов). |
| PATCH | `/listings/{id}/approve` | Одобрить → `active`, устанавливает `published_at`. |
| PATCH | `/listings/{id}/reject` | Отклонить → `rejected` (обязательное поле `reason`). |

| Метод | Путь | Описание |

## 7. Безопасность

### 7.1. Сетевая изоляция админки

Nginx блокирует все запросы на `/admin/*` из внешней сети (`deny all`).
Доступ к админ-панели возможен только из внутренней Docker-сети, в которую
пользователь попадает через WireGuard VPN (порт `51820/udp`) или из локальной
сети сервера.

### 7.2. Аутентификация и авторизация

JWT-токены: `access` — 15 мин, `refresh` — 7 дней. Refresh-токены хранятся в Redis
с TTL и возможностью мгновенной инвалидации. При смене пароля или блокировке
пользователя все его refresh-токены инвалидируются.

Роли: `user`, `moderator`, `admin`. FastAPI-зависимости (`Depends`) проверяют
роль на уровне маршрутов. Middleware логирует все мутирующие действия в админке
в таблицу `AuditLog`.

### 7.3. Двухфакторная аутентификация (2FA)

Реализуется через TOTP (библиотека `pyotp`, RFC 6238). При включении 2FA
пользователю выдаётся QR-код для Google Authenticator / Aegis / любого
TOTP-клиента. При логине, если у пользователя `totp_enabled = true`, после
проверки пароля сервер возвращает промежуточный `totp_token` (JWT, TTL 5 мин)
и требует прохождения `/login/totp`. Для роли `admin` включение 2FA обязательно.
При активации 2FA генерируются одноразовые recovery-коды (8 штук), хранятся
в БД в виде Argon2id-хешей.

### 7.4. Хэширование паролей

**Argon2id** (библиотека `argon2-cffi`). Параметры по умолчанию из
`argon2-cffi` (memory cost 65536 KiB, time cost 3, parallelism 4).
Обоснование выбора: Argon2id — победитель Password Hashing Competition,
устойчив к GPU- и ASIC-атакам благодаря memory-hard алгоритму, рекомендован
OWASP. Bcrypt остаётся приемлемой альтернативой, но Argon2id предпочтительнее
для новых проектов.

### 7.5. Общие меры

**Rate limiting:** на эндпоинты аутентификации — 5 попыток/мин на IP через
Redis (`sliding window`). На остальные мутирующие эндпоинты — 30 req/min.

**CORS:** настроен на список разрешённых доменов (`ALLOWED_ORIGINS` из `.env`).
На `/admin/api/*` CORS отключён (запросы только из внутренней сети).

**HTTP-заголовки безопасности (Nginx):**
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`X-XSS-Protection: 1; mode=block`, `Referrer-Policy: strict-origin-when-cross-origin`,
`Content-Security-Policy` (настраивается под фронтенд),
`Strict-Transport-Security: max-age=63072000; includeSubDomains`.

**Валидация входных данных:** Pydantic v2 на всех эндпоинтах. Максимальная длина
строк задаётся явно. `title` — до 200 символов, `description` — до 10 000,
`body` (сообщения) — до 5 000.

**Загрузка файлов:** проверка MIME-типа (допускаются `image/jpeg`, `image/png`,
`image/webp`), ограничение размера — 5 МБ на файл, максимум 10 файлов на
объявление. Генерация уникальных имён (`UUID`). При загрузке создаётся
thumbnail (400×400, WebP) через Pillow. Оригинал сохраняется без изменений.

**HTTPS:** сертификаты Let's Encrypt (`certbot`), Nginx терминирует TLS.
Автоматическое обновление сертификатов через cron или docker-контейнер certbot.

**Защита от перебора:** при 10 неудачных попытках входа для одного email за 15 мин —
блокировка входа для этого email на 30 мин (Redis key).

10. Миграции и начальные данные
При первом запуске Alembic применяет все миграции (alembic upgrade head).
Seed-скрипт (python -m app.seed) создаёт:

* Суперпользователя (admin) с данными из переменных окружения
(ADMIN_EMAIL, ADMIN_PASSWORD). Для admin сразу генерируется
totp_secret — при первом входе обязательно настроить 2FA.
* Базовый набор категорий (электроника, одежда, мебель, авто, и т.д.)
с корректными slug и вложенностью.

Скрипт идемпотентен — не дублирует данные при повторном запуске
(проверка по email / slug перед вставкой).

11. Требования к dev-окружению
Файл docker-compose.override.yml обеспечивает:

* Hot reload для backend (uvicorn --reload, volume mount ./backend/app).
* Hot reload для фронтендов (Vite HMR, volume mount src/).
* Проброс порта PostgreSQL (:5432) наружу для отладки через DBeaver / pgAdmin.
* Проброс порта Redis (:6379) наружу для Redis Insight.
* Проброс порта MinIO Console (:9001) наружу.
* Отключённый HTTPS (plain HTTP на :80).
* Переменная DEBUG=true — расширенные логи, stack traces в ответах.


12. Логирование и мониторинг
Структурированные логи в формате JSON (structlog или python-json-logger).
Каждая запись содержит: timestamp, level, message, request_id (UUID,
генерируется middleware для каждого запроса), user_id (если авторизован),
method, path, status_code, duration_ms.
Логи пишутся в stdout/stderr (Docker собирает их автоматически).
Healthcheck-эндпоинты:

* GET /api/v1/health — проверка backend (соединение с БД, Redis).
* Docker healthcheck для каждого сервиса в docker-compose.yml.

Метрики (опционально, Этап 6+): Prometheus endpoint (/metrics) через
prometheus-fastapi-instrumentator. Grafana-дашборд для визуализации.

13. Резервное копирование
PostgreSQL: ежедневный pg_dump через cron-контейнер (или host cron).
Хранение: последние 7 ежедневных + 4 еженедельных дампа. Дампы шифруются
GPG и копируются во внешнее хранилище (S3 / удалённый сервер).
MinIO / файлы: синхронизация mc mirror на внешнее хранилище (ежедневно).
Redis: персистентность не критична (кэш + blacklist токенов). RDB-снимки
включены на уровне конфигурации Redis для быстрого восстановления.

14. Соглашения по API
Формат успешного ответа
jsonDownloadCopy code{
  "data": { ... },
  "meta": {
    "page": 1,
    "per_page": 20,
    "total": 150,
    "total_pages": 8
  }
}
Для одиночных объектов meta отсутствует, ответ содержит только data.
Для списков meta содержит информацию о пагинации.
Формат ошибки
jsonDownloadCopy code{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Описание для разработчика",
    "details": [
      {
        "field": "email",
        "message": "Некорректный формат email"
      }
    ]
  }
}

15. Порядок реализации (приоритет)
Этап 1 — Каркас
Docker Compose со всеми сервисами, Nginx-конфигурация, подключение к БД,
Alembic, все модели данных, seed-скрипт, healthcheck-эндпоинт,
структурированное логирование, CI (lint + typecheck).
Этап 2 — Аутентификация
Регистрация, логин, JWT (access + refresh), инвалидация токенов,
роли и permissions, 2FA (TOTP) для админов, сброс пароля, rate limiting
на auth-эндпоинты.
Этап 3 — CRUD объявлений
Создание, редактирование, удаление, смена статуса, загрузка и удаление
изображений (MinIO + thumbnail), пагинация, фильтры, полнотекстовый поиск
(PostgreSQL tsvector), категории (дерево).
Этап 4 — Админка
Админ-фронтенд (SPA), модерация объявлений (approve / reject), управление
пользователями (блокировка, смена ролей), управление категориями,
дашборд со статистикой, журнал аудита.
Этап 5 — Дополнительные функции
Избранное, личные сообщения, уведомления, публичный профиль пользователя.
Этап 6 — Безопасность и деплой
WireGuard-конфигурация, HTTPS (Let's Encrypt), security headers,
CI/CD (автоматическая сборка образов, деплой), резервное копирование,
документация API (Swagger / ReDoc — уже встроено в FastAPI).
